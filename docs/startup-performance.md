# Startup and first-render performance

## Rubric

Use the same machine, build, document, browser version, viewport and power conditions for comparisons. Report the median and 95th percentile alongside the number of samples; a small sample gives only a rough tail estimate. Targets below are initial engineering goals for the reference machine, not guarantees for other systems or pass/fail CI gates.

| Measure                        | Definition                                                                               | Initial goal                               |
| ------------------------------ | ---------------------------------------------------------------------------------------- | ------------------------------------------ |
| App shell                      | Navigation start to two animation frames after the header controls appear                | Median ≤ 200 ms; p95 ≤ 300 ms              |
| First Markdown preview (TTFR)  | Navigation start to two animation frames after the welcome preview reports its DOM ready | Median ≤ 500 ms; p95 ≤ 750 ms              |
| Startup work                   | Assets fetched before the first welcome preview                                          | No diagram or PDF engine until requested   |
| Correctness and responsiveness | Document is visible, controls work, and deferred work can recover from errors            | No regressions in browser and unit tests   |
| Native startup                 | Executable launch to the shell and first document paint, measured in WebKit              | Measure separately before setting a target |

The two-frame marks approximate a painted result, not a direct measurement of pixels on screen or full interactive readiness. The welcome document contains math, code and a diagram placeholder; it does not render the diagram itself. Larger documents, local image reads, compiler invocation, memory use, cold caches and other machines need separate measurements. A browser result must not be presented as a native application launch measurement.

The native benchmark measures from just before spawning the release executable to receipt of an opt-in timing marker from the application. Native markers identify entry to the Rust app and the beginning and end of Tauri's setup callback; they do not separate wrapper execution, dynamic linking, GTK and WebKit initialization into individual costs. The shell marker follows two animation frames after mounting; the folder marker follows directory listing and two frames; the Markdown marker follows the preview's ready signal and two host animation frames; the PDF marker follows PDF.js's first successful page-rendered event and two host animation frames. Additional markers expose file loading, parser and renderer readiness, asset preparation, and frame construction. Markers travel through stderr, and frontend markers also use native IPC, so they include a small, variable reporting delay and can themselves affect performance. They do not prove that every font, image, or asynchronous diagram has finished loading, or measure the compositor's actual presentation. For Typst and LaTeX the benchmark includes compilation and waits for a PDF page; a compilation failure times out rather than reporting a source fallback as a successful PDF render. Compare the same fixture and settings, and test both an ordinary file and representative longer documents.

## Reproduce

Run `npm run build`, then `npm run bench:startup`. The benchmark serves the production build on loopback port 1421 and uses Playwright Chromium. Set `PLAYWRIGHT_CHROMIUM_EXECUTABLE` if Playwright's Chromium is unavailable, and optionally set `PAPYRI_BENCH_SAMPLES` to increase the default ten samples. Each sample uses a fresh browser context within one browser process, so browser startup and OS disk-cache coldness are excluded. Output includes browser and Node versions, individual samples and the resources requested. Run without other intensive workloads; repeat comparisons rather than treating one run as definitive.

For the Linux app, build a release package and run `python3 scripts/benchmark-native.py /path/to/papyri examples/showcase/markdown.md`. Substitute a PDF, Typst, or LaTeX file, or use `examples/showcase` to measure opening the folder and listing its entries. Use `--samples 20` for a more useful tail estimate. Each sample launches a separate process and the script uses a temporary app profile, shared across the samples. The first run may have a colder cache, but subsequent samples and system libraries can be cached; this is not a controlled cold-boot benchmark. Run on the desktop for representative compositor and GPU behavior, or under Xvfb for reproducible headless comparisons. The trace is enabled only for these launches and does not record document contents. The output includes per-stage process-to-marker time and the WebKit navigation-relative time, helping separate process/WebKit startup from frontend work.

To measure selecting a Markdown file after the folder has opened, put `tauri-driver` and `WebKitWebDriver` on `PATH` and run `python3 scripts/benchmark-native-folder.py /path/to/papyri examples/showcase markdown.md`. This measures from the explorer click to the preview's ready signal plus two host animation frames. It does not include application launch or directory loading. Like the launch benchmark, it uses a temporary profile, and its frame-based marker is an approximation rather than a compositor presentation timestamp.

To independently measure WebKit's first contentful paint, run `python3 scripts/benchmark-native-folder.py /path/to/papyri examples/showcase/markdown.md --first-paint`. This reports WebKit's navigation-relative `first-contentful-paint` entry with startup tracing disabled. It excludes launching the executable, WebKit initialization before navigation, and the document preview; it is not a cold-start or total startup measurement. If WebKit does not expose that entry, the benchmark reports an error instead of inventing a time.

For distributions across the showcase, run `python3 scripts/benchmark-native-distribution.py /path/to/papyri examples/showcase results.json --samples 30 --latex fallback`. Use `--latex pdf` when the default LuaLaTeX engine is available. Each randomly ordered launch has a new process and temporary profile, and the script requests Linux file-cache eviction for the app executables and showcase files before each launch. This eviction is advisory; shared libraries, WebKit, fonts, and system caches are not controlled. The output records every marker and any failures. Use the same display and environment for comparisons.

The [histograms](benchmarks/startup-histograms.html) and [raw results](benchmarks/startup-distributions.json) record 30 launches per workload under Xvfb. A separate post-run residency check confirmed eviction of the showcase Markdown file, but the Nix-store executable's residency could not be reliably checked with this user's permissions. These results are fresh-process measurements with attempted targeted eviction, not verified disk-cold or cold-boot timings. LaTeX records the syntax-highlighted source fallback because no engine was installed; Typst includes compilation to its first PDF page. The nearest-rank p95 from 30 samples is a rough tail estimate.

Calling `nix run` includes Nix evaluation and, when necessary, downloading or building dependencies before the executable launches. Time that command separately if it is the user's actual launch path; the native benchmark deliberately measures the built executable and excludes Nix's work.

To avoid repeated Nix evaluation when testing the same build, run `nix build .#papyri` once and launch `./result/bin/papyri path/to/document.md` directly. Rebuild after changing the code. For a Git-backed flake, Nix includes files known to Git; untracked source files must be included before that build can reflect the complete working tree.

## Native reference measurements

On this x86_64 Linux desktop, five launches of the release executable with `examples/showcase/markdown.md` and a temporary profile took a median of 581 ms to the shell and 887 ms to the first preview. The first preview ranged from 868 to 974 ms. These samples used the running desktop session with warm system caches, and include the small IPC and logging delay described above. Approximately 404 ms of the median preview time preceded WebKit navigation (including marker delivery). This estimate is not a direct measurement of process creation alone.

For comparison, three launches through `nix run` against an already-built temporary path flake took 1326, 3779 and 4268 ms to the same preview. This small sample includes Nix evaluation as well as app launch; different flake sources, caches, builds, and system load can change it substantially. A launch during concurrent release compilation took about five seconds, demonstrating that an idle-system median does not capture loaded-system behavior.

An alternating headless comparison of eight warm launches per build tested removing the legacy KaTeX font formats. Median process-to-preview times were 937 ms before and 934 ms after, with overlapping ranges. The font change was not retained: these samples did not establish a meaningful speedup, and dropping fallback formats would reduce compatibility.

## Showcase comparison

With the release executable launched directly under Xvfb, the stage markers for `examples/showcase/markdown.md` showed a baseline median of 145 ms from starting the preview to parser readiness, and 243 ms from building the isolated frame to the document marker. An alternating comparison with eight warm launches per build then measured 938 ms before and 881 ms after prewarming the parser for an initial Markdown file (ranges 907–943 ms and 864–906 ms). Median shell times were 564 ms and 566 ms. This change applies when a Markdown file is passed at launch; directory and PDF launches do not start the parser early.

Six non-interleaved runs each measured showcase-folder readiness at 609 ms before and 607 ms after, and first PDF page at 1085 ms before and 1091 ms after. A WebDriver run of four launches per build measured clicking `markdown.md` inside the already-open folder at 389–400 ms before and 381–403 ms after; that interaction does not benefit from the initial-file prewarm. Three launches of the Typst example on the candidate build reached the first compiled PDF page in a median 1397 ms. These small samples use an isolated profile and warm system caches; they are not cold-start or physical-display measurements.

## Math preview frame investigation

Temporary instrumentation of the built native app opening `markdown.md` from the showcase folder measured approximately 12 ms for sanitizing and inserting the document, followed by approximately 140 ms before the frame's ready message. A diagnostic run replacing the document with a small placeholder was much faster; removing its rendered equations reduced that delay as well. These diagnostic variants did not preserve document content and were used only to locate the cost, not as product changes. Replacing the frame's timer with a microtask shifted the delay rather than reducing it, so the existing scroll-restoration timing was retained.

The app now begins loading the bundled KaTeX font faces in the host while a native Markdown preview likely to contain math is parsed. This is a performance hint: normal isolated-frame rendering remains responsible for loading and displaying the fonts, and a warm-up failure does not prevent the preview. The host retains the loaded faces for the session, trading additional memory for lower latency; delimiter detection can warm fonts unnecessarily for some Markdown syntax or miss unusual math source without changing correctness.

Using the built binaries directly under Xvfb, eight sequential folder-selection samples per build measured a median of 396 ms before and 332 ms after. A second comparison alternating five samples per build measured 403 ms before and 354 ms after. For the showcase's plain `linked.md`, five alternating samples measured 200 ms before and 197 ms after, with substantial variation. Eight alternating direct launches of the math document measured 874 ms before and 872 ms after, which does not establish a meaningful startup improvement. Four non-interleaved samples per build found no apparent folder-opening or PDF regression. These timings use warm caches and an isolated profile; they are not compositor presentation timestamps or cold-start measurements. The native showcase check confirmed the visual equations, MathML, and local image remained present.

## PDF resource loading investigation

On a native baseline run, the median interval from the showcase PDF frame being built to the first-page marker was about 430 ms; the Typst example spent a further 218 ms between source initialization and preview setup, including compilation. A temporary, instrumented version of the PDF runtime attributed roughly 120 ms to the frame reaching its script, 80 ms to worker/document initialization, and 80 ms from page initialization to page rendering. Those stages overlap with other browser work and are not a complete accounting of elapsed time. The seven diagnostic samples included load variation and the instrumentation changed the runtime; these figures are for identifying candidates, not the final comparison.

The PDF frame no longer embeds all PDF.js CMaps, standard fonts and image decoders in its initial script. These resources are still bundled offline, and the isolated frame requests individual files only when needed through the manifest-restricted host bridge. The initial PDF script fell from about 5.0 MiB to 1.9 MiB. A resource that cannot load now produces a visible error and can be retried. A temporary worker-splitting prototype saved only about 10 ms in its initial profile and was not retained.

The following comparison used the final native binaries directly, with warm system caches, isolated profiles, and Xvfb. Direct-launch samples were alternated eight times per build after a warm-up; folder-selection samples were alternated five times per build. Ranges are the smallest and largest observed samples, not confidence intervals or cold-start bounds.

| Workload and endpoint                                     | Before median (range) | After median (range) |
| --------------------------------------------------------- | --------------------: | -------------------: |
| Showcase PDF: executable launch to first rendered page    |   1087 ms (1084–1117) |     957 ms (954–993) |
| Showcase PDF: explorer click to first rendered page       |      581 ms (579–585) |     446 ms (425–453) |
| Showcase Typst: launch, compilation, first rendered page  |   1320 ms (1261–1397) |  1211 ms (1129–1272) |
| CMap-dependent PDF fixture: launch to first rendered page |   1175 ms (1151–1215) |  1123 ms (1112–1131) |

The showcase PDF has embedded fonts and needed no deferred resources for its first page. A separate synthetic PDF required a CMap and rendered its Japanese text in native WebKit; browser tests also exercised an unembedded standard font, missing-resource retry, and path-traversal rejection. These examples do not establish compatibility or speed for every PDF, especially files needing large image decoders or many resources. No LaTeX engine was available for a native LaTeX measurement.

A separate eight-sample stage run of the final binary measured a median 49 ms from preview setup to frame construction (range 47–71 ms), and 372 ms from frame construction to the first-page marker (range 348–404 ms). The corresponding earlier baseline stage run measured 134 ms and 430 ms medians. These stage runs were not interleaved, so the alternating end-to-end comparison above is stronger evidence of the change; the remaining frame-to-page interval is the main candidate for further profiling.

## App shell and Markdown startup investigation

With the built binary and 12 launches per workload under Xvfb, the native-entry and Tauri-setup markers had medians of 84 and 218 ms after process launch. For the folder, the source-ready, shell and listing medians were 541, 569 and 594 ms. For direct Markdown, the preview-start, parser-ready, frame-built and document medians were 545, 656, 674 and 863 ms. Median marker differences are approximate because they are not necessarily from the same launch. WebKit navigation began approximately 400 ms after launch, inferred from frontend marker timestamps and including variable IPC delivery delay. The interval before native entry includes the wrapper and dynamic loading; the setup-to-navigation interval includes WebKit startup and remains unpartitioned. Instrumentation, Xvfb and warm caches limit how representative these values are of a desktop cold launch.

Two further prototypes were tested with twelve alternating launches per build. Starting the initial path request before mounting changed folder listing medians from 587 to 579 ms, but the paired median difference was only 4 ms and Markdown preview regressed from 866 to 878 ms. Starting the Markdown parser from an earlier HTML module left folder listing medians at 582 and 579 ms and Markdown preview medians at 875 and 874 ms, with overlapping ranges. Neither prototype was retained.

Twelve alternating native launches per build tested deferring the preferences and command-palette modules. With the showcase folder as the initial path, the shell medians were 555 ms before and 554 ms after; the difference was not meaningful, so the extra loading states and deferred modules were removed.

Starting renderer asset loading before mounting the host was tested in two variants. In one combined with the deferred panels, the direct-Markdown shell median rose from 565 to 608 ms while the preview median fell from 872 to 846 ms. Fetching without decoding produced a similar tradeoff: shell 573 to 605 ms and preview 875 to 843 ms. Both used twelve alternating launches per build and were discarded because the shell became slower.

A third variant waited for the first animation frame before preloading. Its two-frame shell marker appeared faster in two twelve-pair runs, but the preview did not improve. An independent six-pair native WebDriver comparison with startup tracing disabled reported WebKit first-contentful-paint medians of about 124 ms after navigation for both builds. The apparent shell-marker improvement was therefore not sufficient evidence of an actual paint improvement, and the preload was discarded. This discrepancy also shows why the two-frame marker is an approximation rather than a presentation timestamp.

Finally, a temporary diagnostic worker containing only the showcase's Python highlighter reduced its bundle from 809 KiB to 695 KiB and reduced a seven-sample folder-click median from 334 to 319 ms. The diagnostic omitted other supported languages and changed the worker loading mechanism, so it was not retained or treated as a production speedup. No additional app or Markdown startup optimization from this investigation was retained.

## Upstream research and graphics experiments

The [Tauri maintainers' discussion of AppImage startup](https://github.com/orgs/tauri-apps/discussions/11157) points to compressed packaging as a possible cost; these measurements use the built executable directly. An earlier [WebKitGTK process-launch regression](https://bugs.webkit.org/show_bug.cgi?id=279026) was fixed upstream, while a separate [font-matching issue](https://bugs.webkit.org/show_bug.cgi?id=315135) illustrates that individual WebKit and Fontconfig workloads can be expensive. These reports do not establish that either issue causes Papyri's timings. The current build uses WebKitGTK 2.54.1.

We tested a temporary `lto = "thin"` release build, as described in the [Cargo profile documentation](https://doc.rust-lang.org/stable/cargo/reference/profiles.html). Twelve alternating folder launches per build had baseline/candidate medians of 610 and 606 ms, with a paired median difference of -1 ms. Two twelve-pair Markdown runs had baseline/candidate medians of 912/891 ms and 922/920 ms, with paired median differences of 8 and 6 ms and substantial overlap. The candidate executable was slightly larger and the results did not establish a reliable benefit, so the setting was not retained. The first folder samples were affected by transient load immediately after compilation; all samples remain in the raw data.

On a GPU-backed nested Weston compositor using the laptop's AMD renderer, eight randomized launches per variant measured folder listing medians of 638 ms normally and 519 ms with `WEBKIT_DISABLE_DMABUF_RENDERER=1`; direct Markdown preview medians were 889 and 809 ms. A three-sample check on the actual Wayland desktop measured Markdown at 859 and 760 ms, but the folder timings were highly variable and are inconclusive. All runs used fresh processes, temporary profiles and warm caches. A separate four-run-per-variant scripted scroll test in nested Weston found 32 ms median and 33 ms median p95 animation-frame intervals in both modes, with math and a local image present. It is not a physical frame-presentation measurement or a test of PDF, diagrams, other GPUs or drivers.

The graphics workaround is **not enabled by default**: [Tauri's Linux graphics guidance](https://v2.tauri.app/develop/debug/linux-graphics/) says it disables a faster rendering path and should not be forced on unaffected systems. Users investigating their own setup can try `WEBKIT_DISABLE_DMABUF_RENDERER=1 /path/to/papyri examples/showcase/markdown.md` and compare rendering quality and responsiveness. A software-rendered Wayland test and an Xvfb test also favored the workaround; the Xvfb runtime comparison overlapped a package download and is preliminary. Other tested runtime variants (eager dynamic binding, WebKit system allocator and disabling compositing) did not show a compelling, broadly safe benefit. GLib documents that [`G_SLICE` is ignored](https://docs.gtk.org/glib/running.html) since version 2.76, so it was not tested as a performance change. [Raw experimental samples](benchmarks/startup-forum-experiments.json) include all variants and runs.

WebKitGTK's [Sysprof integration](https://webkitgtk.org/2025/11/26/webkitgtk-2.50.html) exposed events for process launch, style recalculation, layout and painting. CPU stack sampling was denied by the system, and collecting WebKit's event stream increased the observed navigation-relative preview marker from around 466 ms in the earlier ordinary run to 1255 ms in a separate instrumented run. Its event names are therefore useful for identifying work, but those event durations are not baseline timings and cannot be summed because they overlap.

## Directory listing and asset compression

The native directory reader now uses the file type supplied by the directory entry for ordinary files and directories, following the path only for symlinks. It also caches each case-folded sort key for the duration of sorting. Directory symlinks, broken symlinks and the existing case-insensitive directory-first ordering are preserved. Caching sort keys uses temporary memory proportional to the number and lengths of entry names; filesystems that do not provide entry types may still require metadata calls.

Using built release binaries directly under Xvfb with warm caches and two warmups, two randomized 16-pair comparisons on a temporary copy of the showcase with 10,000 extra files measured launch-to-listing medians of 706.4 to 689.4 ms and 706.0 to 691.6 ms. Paired median differences were 17.6 and 20.0 ms. A separate syscall-count diagnostic found 10,000 metadata calls for the added files before and none after on this filesystem; its traced timings were not used. The unmodified showcase folder measured 548.7 versus 550.1 ms, and direct Markdown preview measured 821.3 versus 819.2 ms in 12 pairs, neither establishing a meaningful change. These figures do not establish cold-boot or physical-display performance. The temporary fixture was removed after testing; [raw samples](benchmarks/directory-listing-experiments.json) are available.

Two other diagnostics were not retained. Omitting the embedded preview font definitions made no observable difference in an eight-pair folder-selection comparison and would alter math typography. Disabling Tauri's embedded-asset compression increased the executable from 21.2 to 30.7 MB; 16-pair runs showed no meaningful improvement to the showcase folder or direct Markdown preview. The production configuration keeps the normal compressed assets.

## Preparing Markdown on selection intent

The explorer now starts the Markdown parser worker when a Markdown file receives pointer hover or keyboard focus. It does not read the document until selection, and an unused worker expires after 15 seconds. This moves parser startup into time the user may already spend aiming at or navigating to a file; it does not speed up a direct application launch.

Native release binaries opened the showcase folder under Xvfb with warm caches, temporary profiles, two warmups, and randomized paired samples. Selection measurements run from click to preview readiness plus two animation frames. For the first two rows the simulated hover or focus began 150 ms before clicking; that lead is excluded from the reported latency. Worker instrumentation confirmed construction before the click, not that the worker finished initializing. Ranges are observed minima and maxima, not confidence intervals.

| Selection                   | Samples per build | Before median (range) | After median (range) | Paired median difference |
| --------------------------- | ----------------: | --------------------: | -------------------: | -----------------------: |
| Pointer, 150 ms lead        |                12 |      319 ms (315–339) |     292 ms (279–316) |             35 ms faster |
| Keyboard focus, 150 ms lead |                 8 |      324 ms (317–333) |     292 ms (282–307) |           30.5 ms faster |
| Pointer, immediate click    |                 8 |    324.5 ms (314–335) |     298 ms (293–330) |             23 ms faster |

In separate 12-pair launch comparisons, folder listing medians were 549.1 and 549.7 ms, and direct Markdown preview medians were 822.2 and 817.8 ms; neither establishes a launch improvement. These measurements do not represent a cold boot or physical screen presentation.

Two other prototypes were discarded. Starting the initial Markdown worker from inline HTML produced direct-preview medians of 817.9 and 826.3 ms over 16 pairs. Prefetching preview assets alongside the worker produced a further 7.5 ms paired median improvement in 12 pointer-selection pairs, but would retain the large preview stylesheet after an incidental hover. [Raw samples](benchmarks/markdown-intent-experiments.json) include both experiments.

## Reference result

On x86_64 Linux with Node 24.21.0 and Chromium 154.0.8037.97, ten fresh-context samples gave the following results for the same welcome document and production build configuration:

| Measure                | Before median / p95 | After median / p95 |
| ---------------------- | ------------------: | -----------------: |
| App shell              |        127 / 174 ms |       127 / 151 ms |
| First Markdown preview |      1000 / 1075 ms |       426 / 457 ms |

The first-preview median fell by 57% in this run. The earlier build fetched the approximately 7.3 MiB diagram bundle before displaying the preview; the later build requests it only when a user renders a diagram. Core renderer assets also load in parallel with Markdown parsing. The measurements do not isolate each change's contribution.
